# Agent Note: 桌面壳的生命周期归属与应用内升级

Status: implemented

## Problem

阶段 A 交付的桌面壳（[desktop sidecar shell](2026-08-15-desktop-sidecar-shell.md)）能开窗、能连上运行时、能打成安装包，但它作为一个「应用」还差三件事，而这三件事恰好都不在[阶段 B 可执行计划](../proposed/2026-08-18-desktop-stage-b-executable-plan.md)的 Phase 0–5 里——那五个阶段解决的是把 Cordis host 嵌进主进程、彻底不起 HTTP 服务器，与下面这些正交。

**退出之后服务还在跑。** 发现链的第一档是探测 `127.0.0.1:13080` 上已在服务的实例，命中就附着，而附着分支的 `kill` 是一个刻意的空实现——不是自己拉起的东西不该由自己停掉。这个判断本身没错，错的是安装版也走同一条路：用户双击图标打开应用、用完关掉，机器上却留着一个还在服务的 HTTP 服务器，而界面上没有任何东西告诉他这件事，也没有任何地方能停掉它。

**壳被强杀就留孤儿。** 退出路径会杀掉进程树，但任务管理器结束进程、崩溃、断电都不会走退出路径。留下的运行时继续服务，且没有任何东西再去停它——下一次启动只会再拉一个。

**只重启一次，而且看不见「活着但不干活」。** `onRuntimeExit` 用掉唯一一次重启机会后就停在失败页。一小时挂一次的运行时和每次启动都挂的运行时得到同样的对待，而前者本该用户无感。更麻烦的是另一类故障根本不触发这条路径：事件循环卡死、写操作挂住时进程还活着、socket 还接受连接，退出事件永远不来，用户看到的是一个每个请求都悬着的界面。

**没有升级。** README 里写着更新义务，但没有任何产物满足它。

## Solution

### 归属：安装版只跑自己拉起的运行时

`discovery.ts` 的 `probeOrigin` 现在把空串当作「关闭这一档」，与 `bundledRoot` 已有的语义一致。`main.ts` 传 `process.env.DSH_DESKTOP_PROBE_ORIGIN ?? (app.isPackaged ? '' : DEFAULT_PROBE_ORIGIN)`：安装版不探测，源码检出照旧探测（终端里留着一个 `dsh web` 正是开发时要的效果），显式环境变量在两个方向上都优先——桌面 e2e 的两条通道本来就都显式设置了它，所以两条都不受影响。

于是安装版的 sidecar 一定是 `owned: true`，`quit()` 里本来就有的进程树 kill 就是真正的关停。

### 孤儿：把身份写下来，但要两个证据才敢杀

`owned-runtime.ts`。每次连接成功后把 `{ pid, origin }` 写进 userData，退出时同步删掉；下一次启动在发现链之前把它读回来。

关键是**不能只凭 pid**。操作系统会复用 pid，凭一个数字就动手等于可能杀掉本壳从未启动过的进程。所以记录里带上它服务过的 origin，只有当「pid 还活着」**且**「那个 origin 上仍有 dsh 应答」两条同时成立才执行 kill。要同时误中这两条，需要 pid 被复用、并且恰好有另一个 dsh 占着那个系统分配的端口。pid 已死时连探测都不做——那个 origin 现在可能属于别人。

每条路径都清掉记录，包括抛异常的那条：留过夜的记录会在之后每次启动被重新审视一遍，而每一遍都是 pid 被复用的又一次机会。

### 故障：两类合一，滚动预算

`health.ts` + `restart-policy.ts`。

退出和「不再应答」按同一件事处理，因为对使用者来说结果一样。后者靠主动探测发现：用当初准入这个运行时的同一个 `host.describe` 握手，每 15 秒问一次，连续 3 次没应答才算故障——单次不算，笔记本从睡眠恢复就会丢一次。任何一次应答清零计数，所以报的是「不再应答」而不是「应答得慢」。watch 在报故障之前先停掉自己，这样一次连接最多报一次故障，重连过程不会被上一个 watch 打断。

重启预算是**滚动窗口**而不是终身计数：十分钟内三次，退避 0 秒 → 5 秒 → 30 秒，超出窗口的故障被遗忘。于是一小时挂一次的运行时永远会重启且用户无感，每次启动都挂的会耗尽预算、停在加载页并附上日志尾部。重试按钮恢复完整预算——用户按下它这件事本身是窗口不掌握的信息，也许他刚腾出了那个一直被占的端口。

### 升级：不用 electron-updater

这不是取舍偏好，是打好的包里看得见的事实：`electron-builder.yml` 写了显式的 `files` 列表，asar 里只有 `lib/`、preload 和加载页，**完全没有 `node_modules`**。在 `apps/desktop` 加一个运行时依赖，它不会出现在安装后的应用里，第一次 `import` 就崩。第二个原因是 macOS：原地应用更新需要已签名的应用，而本 fork 的 macOS 构建没有签名，那个库最招牌的能力恰好在最难手写的平台上不可用。

剩下的部分小到可以自己拿住（`updater.ts`）：

- **发现**走 GitHub API 的 JSON，所以这一步不需要 YAML 解析器。
- **版本号从 tag 的任意位置读**，不认死 `v` 前缀。本仓库的发布工具打的是 `dsh-v0.3.1`，恰好是标准 tag 解析器读不出来的形状——这条是让发布命名维持现状、不必为升级机制改造发布流程的关键。
- **同扩展名下优先选安装器**。Windows 的安装器和便携版都是 `.exe`，只有前者能原地替换已安装的应用，取第一个匹配会 stage 一个更新不了任何东西的文件。
- **校验**用 electron-builder 本来就会生成在安装包旁边的 `latest*.yml` 里的 `sha512`。解析器是刻意写窄的：那个文档是生成的、形状固定，且校验和解析失败必须读作「没有」而不是「答案错了」。不通过是拒绝安装而不是给警告——下一步就要把这个文件交给操作系统以用户权限执行。
- 发布时没带 channel 文件的旧版本会在未校验的情况下下载，并在日志里说明是哪一种情况；这个区别对事后查问题的人是有意义的。
- **安装器只在运行时已经停掉之后、作为退出路径的最后一步启动**，因为它要替换的正是本进程正在使用的文件。

检查时机：托盘一个手动入口，加上连接成功 20 秒后一次无人值守检查——放在窗口已经可用之后，不放在启动过程中，那会和运行时抢同一条刚建立的网络。检查没发现新版就什么都不说。`checkForUpdate` 的每一条失败路径都返回 `unavailable` 而不是抛异常：无人值守的检查不该把一次断网变成一个要用户去关掉的错误框。

`electron-builder.yml` 的 `publish` 显式写明本 fork。此前它是从 package 清单的 `repository` 推断的，而那指向上游——打出来的 `app-update.yml` 里写着 `deepseek-ai/deepseek-harness`，每一个安装后的应用都会去查一个从来不含这些构建的发布通道。发布工作流同时上传 `latest.yml` / `latest-mac.yml`。

### 顺带修掉的一处

`compareVersions` 抽到 `version.ts` 给发现链和升级检查共用，同时修正了预发布版本的排序：原来 `0.4.0` 排在 `0.4.0-rc.1` **之前**，意味着 npx 缓存里会挑 rc 而不是正式版，升级检查也会告诉一个装着 0.4.0 的用户「0.4.0-rc.1 是更新」。原实现没有任何测试钉住这个行为。
