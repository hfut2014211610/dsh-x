# Agent Note: 一轮实机反馈的修复——启动、伴随栏、工作区阅读与产物跟随

Status: implemented

## Problem

0.3.2 安装包交付验收后，一轮实机使用提出七个问题。它们表面上分散在桌面壳和 Web 客户端两侧，但有一个共同点值得先说：**没有一个能靠读代码猜出来**，每一个的真实根因都和第一眼的判断不一样。这份笔记记录的是那些差异，而不是改动清单——改动在各自的 commit 里。

## 各问题的真实根因

### 启动卡顿：不是慢，是卡在了绘制的那条线程上

发现链和首次解压本来就要花时间，问题在于它们花在哪儿。`main.ts` 的 `execFile` seam 与 `ensureBundledRuntime` 的 `extract` 都用 `spawnSync`，而这两处跑在 **Electron 主进程**上——那条线程同时持有窗口和给加载页推状态的 IPC。于是「正在汇报启动进度的那块屏」在启动期间恰恰不能重绘。

两者里更重的是首次解压：冷机器上要在杀毒实时扫描下写出几万个小文件，超时上限写的是 900 秒。也就是说首次运行最长可以冻住主进程十五分钟，而屏幕上什么都不动。

改成异步之后，两处的截止时间从 `spawnSync` 的 `timeout` 变成显式的定时器，语义不变。

顺带把安装版的发现链改成**优先用自带的运行时**。安装包内嵌运行时的意义就是不依赖机器上碰巧有什么；本机没有全局 `dsh`，所以每次启动都要白跑一次 shell 拉起（约 200ms，修复前是主进程冻结）再扫 npx 缓存。这既是性能也是正确性。

### 伴随栏拖宽后 composer 不跟：驱动错了对象

`ResizeHandle` 加上之后，拖动改的是面板自己的 `flex-basis`。但常驻 composer 是**一个共享实例、绝对定位在框架上**，宽度取自 `calc(var(--dsh-companion-width) - ...)`，而且它是 `conversation.session` 这个 slot 的**兄弟节点**，不是后代——在 session 内部设任何样式都到不了它。

正确做法是驱动那个自定义属性本身，写在声明它的元素上（`.root`，加了 `data-conversation-root` 便于定位）。面板和 composer 都从同一个属性取值，于是一起动。离开伴随布局时要把属性移除，否则一个曾经拖宽过的会话会把那个宽度一直摁在后续布局上——这一条不能只在卸载时做，因为切走视图时组件并不卸载。

### 伴随栏内容溢出：不是文字不换行

换行规则本来就齐（`overflow-wrap: anywhere` 到处都是）。真正的原因是两层：

`[data-conversation-companion] .root` 给了 `min-height: 0` 却没给 `min-width: 0`。它是伴随栏主体的 flex item，默认取内容最小宽度，于是一个不换行的代码块或终端卡片就把整条对话流撑到栏外，**里面所有内容随之按更宽的量排版**再被裁——这才是「文字看起来不换行」的由来；在中间栏同样的内容只是恰好放得下。

补上之后还剩一个，而且是看不见的那个：回合尾部的统计行（`用时 2分04秒 · 首 token 2.7秒 · 121 tok/s`）是 `white-space: nowrap` 且 `min-width: auto`，不能被压缩，在 385px 的栏里外溢约 150px。它平时 `opacity: 0` 悬停才显示，所以肉眼看不到它，却让整列有了横向滚动。实测 `scrollWidth` 533 对 `clientWidth` 385，改完后相等。

### 产物不自动打开：两个视图都只认「已经打开的那个」

`UedView` 与 `WritingView` 的变更订阅都写着「路径不等于当前打开的就返回」。于是本轮刚生成的产物既不会打开，在设计侧**连列表都不会刷新**（`refreshListing` 只在目录变化时跑），所以想手动点都点不到。

改成**跟随最新产物，直到用户自己点选**。三条边界值得记：设计侧要先刷列表再选中，因为新写的文件还不在列表里；跟随要能跨目录，否则线程一旦开始整理输出就正好不跟了；编辑器里未保存的改动优先级最高，既不能被重载冲掉，也不能被跟随甩在后面。

### 阅读器只有 markdown 有阅读视图

`DocumentFormat` 早就有 `code`/`docx`/`xlsx`，`documents-local` 也确实能从 zip 里抽出 Word 和 Excel 的文本——但视图只判断了 `format === 'markdown'`，其余一律落进 `<textarea>`。于是源码文件用编辑框读，Word 文件把「从 zip 里抽出来的文本」当成源码给你看。

现在每种有东西可渲染的格式都有阅读视图，模式切换也从 markdown 专属变成通用。纯文本仍然直接进编辑器且不提供切换——它读起来就是同样的字符同样的顺序，编辑器已经在显示了。代码阅读视图是通栏而不是 760px 的阅读宽度：代码靠缩进读，一个窄栏会把作者对齐好的东西折断。

## 未解决，且不该被误认为已解决

**写作工具产不出合法的 Word 文档。** `documents-local` 的 `create` 走 `fs.writeText`，写的是纯文本。要求模型输出 Word 文档时，它只能写一份 HTML 命名为 `.doc` 交差——本轮实机产物 `docs/产品说明书.doc` 正是这样一个文件。读取侧已经修好，生成侧需要一个 docx 写入器，是独立的一块。`.doc`（2007 前的二进制格式）另需 OLE 解析器。

**写作产物落进了受管目录。** 同一次会话把产物写进仓库的 `docs/`，那里受双语配对与相对链接门禁管辖，于是 `verify-translation-pairing` 与 `verify-md-links` 双双变红。产物落点需要避开受管目录，或者门禁需要认得产物——两者都还没做。

**连接器页无法真正接入飞书。** 卡片的五个字段与插件 `Config` 一一对应，但只在插件已挂载时显示；`packages/host/plugin-inventory` 是只读的，没有安装或启用接口，所以页面只能给出一条命令行指引。

**UED 预览只能看不能标注。** 预览 iframe 是 `allow-scripts` 且刻意不与 `allow-same-origin` 同列，隔离由双向单测与 web e2e 双重断言。要做元素拾取与标注，必须往预览注入受控脚本并经 postMessage 通信，且不能破坏那些断言。

## Verification

各包单测（ui-conversation / ui-primitives / ui-trajectory 1049 个，ui-writing 与 ui-ued 45 个，apps/desktop 73 个）、`agent-preset-selection` 的 8 个 web e2e、typecheck 与 lint 全绿。伴随栏两处几何在开发服务器上实测过前后数值，桌面加载页在真实 Electron 窗口里截图核对过成功与失败两条路径。仓库门禁中 `verify-md-links` 与 `verify-translation-pairing` 因上述会话产物为红，与本轮改动无关。
