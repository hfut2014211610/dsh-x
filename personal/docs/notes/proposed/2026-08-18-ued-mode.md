# Agent Note: UED 模式——并发迭代的 HTML 原型设计

Status: proposed

B 阶段已落地（`apps/cli/config/agent-presets/ued/`），实际组合与三处与本文的偏差见[实施笔记](../implemented/2026-08-18-ued-mode-preset.md)。本笔记留在 `proposed/`，因为 C 阶段预览视图尚未开始。

**下文涉及 Open Design 的内容已作废（2026-08-18 决定）**：不引入第三方设计工具，不 vendor 第三方设计系统，也不再走"先跑一遍 MCP 路线"这个先决动作。因此"从 Open Design 借鉴什么"整节、B 阶段的 vendor 事项、备选方案的第一条，以及风险表中"Apache-2.0 与 fork 的 MIT 混用"、"上游设计系统漂移"两行均不再适用。设计规范的接入点保留（预设内 skill 根），但只用于自撰内容。

取代 [dsh-x-wireframe 原型图插件](../rejected/2026-08-17-wireframe-plugin.md)。

## 问题

dsh 没有面向 UI 设计的模式。要画原型只能切到外部工具，手工把想法翻译成图形再带回会话——模型既看不到产物，也无法按指令修改它。

真实的设计工作有两个形态特征，是任何"一句话出图"方案都无法覆盖的：

- **迭代为主，生成为辅。** 首次生成只占很小一部分，绝大多数时间在既有产物上反复调整。
- **指令短频快。** "按钮改圆角"「这块间距太挤」「换成深色底」——每条都很小，但一条接一条。若每条都阻塞主会话等待完成，交互节奏被彻底破坏。

第二点决定了架构：修改必须能从主会话**分线程并发**执行。

外部方案 [Open Design](https://github.com/nexu-io/open-design)（Apache-2.0，88k stars）不适合直接复用：它是宿主应用，把 dsh 当作后端 coding agent runtime（`apps/daemon/src/runtimes/defs/deepseek-harness.ts`），方向与"dsh 内的能力"相反。但它的产物形态与设计系统资产值得借鉴。

## 提案

新增 **UED 模式**，分两阶段。B 阶段是纯组合（一个约 20 行的 policy 包加 preset YAML），C 阶段才写客户端代码。

核心判断：**产物是自包含 HTML，不发明中间表示**；**存储、编辑、并发、任务可见性全部复用 dsh 现有能力**。

### 复用矩阵

| 能力 | 现成件 | 说明 |
|---|---|---|
| 产物读写与版本守卫 | `ctx.documents` / `document_*` | `documents-local` 的 `formatOf()` 无白名单，`.html`/`.css`/`.svg` 落入 `'code'` 分支；`edit()` 传入 guarded base version，冲突抛 `DOCUMENT_STALE_VERSION` |
| 分线程并发 | `tool-subagent`，`backgroundMode: continuable` | 返回 `{ kind: 'continuable', subagentId }`，子 agent 拥有自己的 turns 与 transcript，主会话不阻塞 |
| 持续投递短指令 | `send_message`（`tool-subagent-control`） | 向已存在的子线程发新工作，是"短频快"的载体 |
| 子线程继承设计上下文 | `subagent-fork-in-process` | 以父会话已完成的 turns 为种子，精确切到最后一个 `turn/end`，不含进行中的半截 turn |
| 并发可见与取消 | `ctx.jobs` + `ui-jobs` | session header 列出 running/stopping，badge 计数；是取消操作唯一的挂载点 |
| 钻进子线程 | `ui-subagent` | 导航到子线程 transcript |
| 产物打开 | `ui-deliverables` | 成功写文件自动成为聊天里的可点击 chip，经 Host opener 打开 |
| 设计规范加载 | `ctx.skills` + `skill-filesystem` + `skill_search`/`skill_load` | 解析的正是 `SKILL.md`，与 Open Design 同格式；`customSkillDirs` 可配独立根 |

### 从 Open Design 借鉴什么

**借鉴** `design-systems/`：154 个包，Apache-2.0。以 `apple` 为例，`DESIGN.md` 17.8 KB（给 agent 读的设计规范散文）、`DESIGN-zh.md` 16.8 KB、`tokens.css` 16.7 KB、`manifest.json` 1.3 KB。以 `SKILL.md` 形式 vendor 进插件的 skill 根目录，由 `skill_load` 按需取用。

**不借鉴** `skills/`：164 项里多数是指向上游仓库的目录占位（`upstream:` 字段），本体不在库内。抽查 `ui-ux-pro-max` 明说"完整模板与搜索工作流未打包"，`web-artifacts-builder` 正文仅约 95 词。

**体积约束**：单个设计系统含 15 种语言约 340 KB，154 包约 52 MB，全量 vendor 不可行。只取 `DESIGN.md + DESIGN-zh.md + tokens.css + manifest.json` 时单包约 53 KB，挑 5 个约 263 KB。

### 并发冲突策略

版本守卫保证**不丢更新**，但挡不住**语义冲突**：A 把主按钮改蓝、B 把同一按钮改绿，B 撞 `DOCUMENT_STALE_VERSION` 后重读重做，结果是后到者静默覆盖，两边都报成功。

策略按优先级固化进 policy section：

1. **按产物分线程**（首选）——一个线程负责一个 screen 或一个文件。多屏原型天然可分，零冲突。
2. **撞了就重读重做**——收到 `DOCUMENT_STALE_VERSION` 后重读最新内容再施加自己的改动，等价 rebase。单文件精修时的兜底。
3. **主线程串行落盘**——子线程只产出建议，主会话统一 apply。最安全但并发收益归零，仅在前两条都不适用时启用。

policy 必须明确：**跨线程修改同一视觉元素前先回主会话确认**，因为这是版本守卫覆盖不到的盲区。

### B 阶段——UED preset

```yaml
- id: persona          # 设计人格
- id: ued-mode         # 并发与冲突 policy section（唯一新代码，对标 writing-mode 的 21 行）
- id: tool-documents   # 复用，HTML 走 'code' 分支
- id: tool-subagent    # config: provider=fork, backgroundMode=continuable
- id: tool-subagent-control   # send_message
```

外加 `personal/plugins/dsh-x-ued/skills/` 下 vendor 的 3–5 个设计系统。

不写 schema，不写渲染器，不写客户端代码。产物在外部浏览器查看。

### C 阶段——预览视图

`personal/plugins/dsh-x-ui-ued/`，经 `ctx.slots.inject('conversation.view', ...)` 注册，与 `ui-writing` 走同一 seam（该包全量 865 行，含编辑器、文件树、大纲、搜索、预览切换；UED 视图若只做文件列表加 iframe 预览会明显更小）。`documents/changed` 事件驱动刷新。

## 备选方案

**直接用 Open Design（经 MCP 挂进 dsh）。** dsh 自带 `packages/mcp/mcp-client/`，把外部 MCP server 的工具注册为 `mcp__<server>__<tool>`。零开发即可获得其全部设计能力。**未选择的原因**：产物是 output-focused、非双向可编辑的 artifact，且预览在独立桌面应用内，拿不到"dsh 会话内并发迭代"这个核心诉求。**但这条路应先跑一次**——如果它已经够用，本方案整体可以取消。

**保留原 JSON + SVG 方案。** 见[废弃笔记](../rejected/2026-08-17-wireframe-plugin.md)的废弃原因表。

**并入写作模式而非新建模式。** `document_*` 工具是通用的，HTML 迭代今天用 writing preset 就能跑。**未选择的原因**：writing preset 只有三行（persona + writing-mode + tool-documents），没有挂 subagent 工具，拿不到并发；且设计人格与写作人格、并发策略与文档策略都不同，混在一个 preset 里会互相污染。

## 验收标准

**B 阶段。**

- `dsh --profile <p> --agent-preset ued` 启动后，工具集只含 `document_*` 与 subagent 三件套，不含编码工具。
- "做一个登录页原型" → workspace 出现自包含 HTML → 聊天里 deliverables chip 点开即在浏览器渲染。
- 连续下达三条修改指令，主会话均不阻塞；`ui-jobs` 中可见对应的 running 记录并可取消。
- 两个线程改同一文件时，落后者收到 `DOCUMENT_STALE_VERSION` 并按策略 2 重做，最终内容包含两次修改而非丢失其一。
- 跨线程修改同一视觉元素时，模型按 policy 回主会话确认而非各改各的。

**C 阶段。**

- 预览面板渲染当前 HTML 产物；子线程写入触发 `documents/changed` 后面板自动刷新。
- 原型内脚本无法访问宿主页面的 RPC 通道（见风险）。
- 多线程并发修改时预览不闪烁、不显示中间态破碎内容。

## 风险

| 风险 | 对策 |
|---|---|
| **iframe 沙箱逃逸**（C 阶段唯一真难点） | dsh 客户端目前无 iframe 基础设施（`git grep iframe` 在 `packages/client/` 下无实质命中）。模型生成的 HTML 会带脚本，必须 `sandbox` 属性隔离 + CSP，且必须在 `api-request-trust.ts` 那条信任边界之外。此项单独评审，不与功能一起赶工 |
| 语义冲突静默覆盖 | 版本守卫覆盖不到。靠 policy 强制"按产物分线程"优先，跨线程改同一元素先确认 |
| 并发线程数失控 | policy 限定同时活跃线程数；`ui-jobs` 提供取消挂载点 |
| Apache-2.0 与 fork 的 MIT 混用 | vendor 设计系统需保留 LICENSE、NOTICE 与出处声明 |
| 上游设计系统漂移 | Open Design 仍高频推进（2026-08-18 已到 PR #6999），vendor 即快照，需人工同步；`manifest.json` 记录来源 commit |
| B 阶段跑通后发现 MCP 路线已够用 | 这是好结果，不是风险。B 阶段成本足够低，可承受被证伪 |
