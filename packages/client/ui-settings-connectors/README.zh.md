# @deepseek-ai/dsh-client-ui-settings-connectors

[English](README.md) | 中文

连接器设置页。它注册一个 `settings.section` 入口（`connectors`），列出所有能从外部接进 dsh 的应用渠道；把 `settings.connector.item` 声明为渠道自己挂卡片的位置；并自带飞书渠道那张卡片。宿主侧没有任何行为：每张卡片通过 `ctx.settingsScope` 改自己那个渠道的配置命名空间。

## 为什么不做成"插件"页下面的一个标签

连接器不是 agent 循环上的旋钮。它是外面进来的一条路，通常还要用户自己起一个进程；而且跟其他设置页都不一样——**恰恰是东西还没装的时候**，这一页才最该打开。

最后这点就是看得见的差别。插件页对没有装的插件什么都不画，这在那边是对的：一个从没挂过 shell 执行器的部署，不该露出它的限额。这里反过来。只列已经有的渠道，回答不了"我还能接什么"，所以没装的渠道照样占一行，挂一个"未安装"角标，并给出装它的那一行命令。没装的卡片唯独不给控件：没有命名空间可写，摆一排禁用的输入框只会引人去试。

## 加一个渠道

第二个渠道自己一个包，不用改这个包：

```ts
ctx.slots.inject('settings.connector.item', () => ctx.slots.register({
  name: 'settings.connector.item',
  id: 'dingtalk',
  order: 10,
  locale: NS,
  inject: () => controller.inject(),
}, DingTalkCard))
```

卡片外壳（`ConnectorCard`）、两种控件（`ValueField`、`ChoiceField`）和暂存表单（`ConnectorForm`）都是本包内部的东西——客户端打包门禁不允许跨包 import 这些值，所以想要同一套外壳的渠道应该把卡片注册到这里，而不是在别处再实现一遍。

## 暂存表单

卡片先把用户输入的内容留着，按保存才写。每一次设置写入都是一次带版本围栏的持久化文档变更，控件要是一边输入一边提交，等于把一次敲键盘变成一次没人要求、也没法预览的写入。

字段显示的是生效值——用户层盖组合层、组合层盖 schema 默认值——以及用户层里有没有这一条。标记"已改过"看的是**这一条在不在**，不是值相不相等：改成跟组合层默认值一样，那也是改过。保存后的结果从段里读回来，不是在本地预测，因为宿主的校验器持有 schema 表达不了的约束；没存成功的那次保留草稿，可以接着改，不用重新输一遍。

## 飞书卡片

`dsh-x-feishu` 的五个字段：飞书开的会话用哪个预设、卡片密度、卡片正文两次推送之间最少隔多久、审批卡片等人点多久、桥接端点。

凭证是特意不放的。飞书应用和它的密钥在 `lark-cli` 后面的系统 keychain 里，由桥接进程持有；插件一个都不存，这一页也不存。

## Model Experience

没有。本包只改宿主已经拥有的配置，不注册工具、提示段或结果投影。

#### KV Cache effect

没有；本包既不组装也不发送模型请求。

## 已知限制与待办

- **只看是否装上，不看是否活着。** 角标说的是部署有没有装这个插件，不是桥接进程起没起、socket 连没连上。要报后者，得让渠道插件提供一个状态接口，目前一个都还没有。
- **导航行用的是兜底图标。** `ui-settings-general` 把 section id 映射到图标，那是本 fork 不改的上游文件，所以 `connectors` 画的是通用设置图标。
- **桥接自己的配置够不着。** 名单、事件配置目录、机器人 open id 都在桥接的 `config.json` 里，不在设置命名空间里，这一页看不到也改不了。
- **安装包里不带飞书插件。** 发行流程只打 `packages/*/*` 和 `apps/*`，而这个渠道在 `personal/` 下，所以装出来的应用里这张卡片一直是"未安装"，要手动把插件目录挂进 profile。
